## Module 8.3: Storage for Large-Scale AI

### The AI Storage Challenge

Training large language models requires storing and accessing massive datasets efficiently:

* **Training data**: 100s of TB to PBs (web scrapes, books, code)
* **Checkpoints**: TBs per checkpoint, multiple checkpoints per training run
* **Logs and metrics**: GBs to TBs of telemetry
* **Model artifacts**: Multiple versions, experiments

Traditional storage systems struggle with:
* **Scale**: Petabyte-scale datasets
* **Throughput**: Thousands of GPUs reading simultaneously
* **Latency**: Can't starve GPUs waiting for data
* **Cost**: Balance performance and economics

### Storage Hierarchy

AI training uses multiple storage tiers:

```
Tier 1: GPU Memory (HBM)
├─ Size: 80-640 GB per GPU
├─ Bandwidth: 2-3 TB/s
└─ Latency: <1 μs

Tier 2: Local NVMe SSD
├─ Size: 1-16 TB per node
├─ Bandwidth: 14-28 GB/s (PCIe 4.0 x4)
└─ Latency: 10-100 μs

Tier 3: Parallel Filesystem (Lustre, BeeGFS)
├─ Size: 1-100 PB per cluster
├─ Bandwidth: 100-1000 GB/s aggregate
└─ Latency: 1-10 ms

Tier 4: Object Storage (S3, Blob)
├─ Size: Unlimited (exabytes)
├─ Bandwidth: Variable
└─ Latency: 10-100 ms
```

### Local NVMe Storage

**NVMe SSDs** in compute nodes provide fast local storage:

#### Use Cases

* **Checkpoint staging**: Write checkpoints locally first
* **Dataset caching**: Cache hot data close to GPUs
* **Temporary files**: Intermediate results, shuffling
* **Burst I/O**: High-speed reads during data loading

#### Benefits

* **High bandwidth**: 7-14 GB/s per drive
* **Low latency**: 10-100 microseconds
* **Parallel access**: Each node independent
* **Cost-effective**: $100-200 per TB

#### Limitations

* **Capacity**: Limited by node storage (1-16 TB typical)
* **Durability**: Data lost if node fails
* **Not shared**: Can't access from other nodes
* **Management**: Needs orchestration for multi-node

### Parallel Filesystems

**Parallel filesystems** provide high-performance shared storage:

#### Lustre

**Lustre** is the dominant parallel filesystem for HPC and AI:

##### Architecture

```
Clients (Compute Nodes)
    ↓
Metadata Servers (MDS) ─ Manages namespace, directory structure
    ↓
Object Storage Servers (OSS) ─ Store actual data
    ↓
Object Storage Targets (OST) ─ Underlying storage (RAID groups)
```

##### Characteristics

* **Scalability**: 100+ PB, 1000+ GB/s throughput
* **POSIX compliant**: Standard file interface
* **Parallel access**: Multiple clients, multiple servers
* **Striping**: Files split across OSTs for bandwidth
* **Open source**: Wide adoption, mature

##### Stripe Configuration

```bash
# Set stripe count for large files
lfs setstripe -c 16 /lustre/datasets/
# Each file striped across 16 OSTs
# Aggregate bandwidth: 16 × OST_bandwidth
```

**Optimal stripe count**: 1-2× number of nodes reading file

#### BeeGFS

**BeeGFS** (formerly FhGFS) is an alternative parallel filesystem:

##### Characteristics

* **User-space**: Easier to deploy than kernel-space Lustre
* **Native RDMA**: InfiniBand/RoCE support
* **Metadata scaling**: Better small-file performance
* **Buddy mirroring**: Built-in replication
* **Commercial support**: ThinkParQ provides enterprise version

##### Use Cases

* Clusters where ease-of-deployment valued
* Workloads with many small files
* Sites without Lustre expertise

#### Performance Comparison

| Filesystem | Max Scale | Throughput | Metadata Ops | Maturity | Complexity |
|-----------|-----------|------------|--------------|----------|------------|
| Lustre | 100+ PB | 1000+ GB/s | Good | Very High | High |
| BeeGFS | 50+ PB | 500+ GB/s | Excellent | High | Medium |
| GPFS/Spectrum Scale | 100+ PB | 1000+ GB/s | Excellent | Very High | Very High |
| NFS | 10 PB | 100 GB/s | Poor | Very High | Low |

### Data Loading Patterns

#### Sequential Reading (Efficient)

```python
# Reading large files sequentially
# Good for parallel filesystem
for batch in dataset:
    train_step(batch)
# Filesystem can prefetch, optimize layout
```

#### Random Access (Challenging)

```python
# Random sampling from dataset
# Stresses metadata server
for epoch in range(num_epochs):
    shuffle(dataset)  # Metadata operations
    for batch in dataset:
        train_step(batch)
```

**Solution**: Pre-shuffle or use sharded formats

### Dataset Formats

#### Optimized Formats for AI

**WebDataset (TAR-based)**:
```
dataset.tar contains:
  img00001.jpg, img00001.json, img00001.txt
  img00002.jpg, img00002.json, img00002.txt
  ...
```

* Sequential access patterns
* No metadata lookups during training
* Easy to stream from object storage

**TFRecord/RecordIO**:
* Binary format with length-prefixed records
* Sequential access optimized
* Integrated with TensorFlow/PyTorch

**Parquet/Arrow**:
* Columnar format
* Efficient for tabular data
* Good compression

#### Anti-Pattern: Many Small Files

```
dataset/
  train/
    img00001.jpg (50 KB)
    img00002.jpg (50 KB)
    ...
    img10000000.jpg (50 KB)
```

**Problem**: 10M files = 10M metadata operations
**Solution**: Pack into sharded archives (1000-10000 images per shard)

### Caching Strategies

#### In-Memory Caching

```python
# Cache entire dataset in RAM (if fits)
dataset = load_dataset().cache()
# First epoch: Load from storage
# Subsequent epochs: Load from RAM
```

**Works for**: Datasets < total cluster RAM

#### Local SSD Caching

```python
# Cache to local NVMe
dataset = load_dataset().cache('/local/ssd/cache/')
# Populate local cache on demand
# Subsequent access: Local SSD (fast)
```

**Works for**: Datasets < local SSD capacity

#### Distributed Caching

Use Redis, Memcached, or similar:
```python
# Shared cache across nodes
cache = DistributedCache(redis_cluster)
if not cache.exists(key):
    data = load_from_storage(key)
    cache.set(key, data)
else:
    data = cache.get(key)
```

### Checkpoint Storage Strategy

Checkpoints are critical and large:

#### Checkpoint Patterns

**Local Write + Async Upload**:
```python
# Fast write to local SSD
save_checkpoint('/local/ssd/checkpoint.pt')
# Asynchronous upload to shared storage
async_upload('/local/ssd/checkpoint.pt', '/lustre/checkpoints/')
# Continue training immediately
```

**Direct Write with Parallel I/O**:
```python
# Each rank writes its portion in parallel
torch.save(model_shard, f'/lustre/checkpoints/rank_{rank}.pt')
# Parallel filesystem aggregates bandwidth
```

**Incremental Checkpointing**:
```python
# Only save changed parameters
delta = compute_delta(current_model, last_checkpoint)
save_checkpoint(delta)
# Smaller, faster writes
```

### Network-Attached Storage (NAS)

**NFS** still used in some deployments:

#### Characteristics

* **Easy setup**: Mature, well-understood
* **Good for**: Small clusters (<100 nodes)
* **Limitations**: Metadata bottleneck, limited scalability
* **Use case**: Development, small-scale training

### Object Storage

**Object storage** (S3, Azure Blob, GCS) for long-term data:

#### Characteristics

* **Capacity**: Unlimited scale
* **Durability**: 99.999999999% (11 nines)
* **Cost**: $20-25 per TB/month
* **Latency**: 10-100 ms (too slow for training)
* **Bandwidth**: Limited per-request

#### Use Cases

* **Dataset archival**: Long-term storage
* **Transfer between sites**: Move data between datacenters
* **Backup**: Disaster recovery
* **Pre-training data**: Download once, cache locally

#### Access Patterns

```python
# Don't: Read from S3 during training (slow)
for batch in s3_dataset:  # ❌
    train_step(batch)

# Do: Download to local/parallel filesystem first
download_from_s3(s3_dataset, '/lustre/datasets/')  # ✓
for batch in local_dataset:
    train_step(batch)
```

### Storage Network

Dedicated storage network separate from compute network:

```
Compute Network: InfiniBand for GPU-GPU
Storage Network: 100-400G Ethernet for storage traffic
```

**Benefits**:
* Isolation: Storage traffic doesn't impact training
* Optimization: Different protocols (NFS, SMB, S3)
* Cost: Cheaper Ethernet for non-latency-sensitive traffic

### I/O Profiling and Optimization

#### Common Bottlenecks

* **Metadata operations**: Too many small files
* **Sequential vs random**: Random access is slow
* **Stripe configuration**: Wrong stripe count/size
* **Client contention**: Too many clients, too few servers
* **Network congestion**: Shared network with compute

#### Profiling Tools

* **darshan**: I/O profiling for HPC applications
* **iostat**: Linux I/O statistics
* **Lustre stats**: `lfs df`, `lctl get_param`
* **Application profilers**: PyTorch Profiler shows I/O wait time

### Best Practices

#### Data Loading

* Use **multi-threaded data loaders** (`num_workers>0`)
* **Prefetch** next batch while training current batch
* **Pin memory** for faster CPU→GPU transfers
* **Use efficient formats** (WebDataset, TFRecord)

#### Checkpoint Management

* **Checkpoint to local SSD first**, async upload
* **Keep only N recent checkpoints** (delete old ones)
* **Verify checkpoint integrity** after write
* **Test restoration** regularly

#### Dataset Preparation

* **Shard datasets** into 100 MB - 1 GB files
* **Sequential layout** for reading efficiency
* **Pre-shuffle** if possible to avoid random access
* **Compress** text data (use gzip, zstd)

### Cost Considerations

Storage cost for large-scale training:

#### Example: 175B Parameter Model Training

```
Training data: 500 TB (CommonCrawl, books, code)
Checkpoints: 2 TB per checkpoint × 100 checkpoints = 200 TB
Logs/metrics: 10 TB
Total: ~710 TB

Lustre storage ($100/TB/year): $71,000/year
S3 archive ($25/TB/year): $12,500/year
NVMe cache (1 TB per node × 1000 nodes): Capital cost
```

### Future Trends

* **CXL** (Compute Express Link): Memory pooling across servers
* **NVMe-oF**: NVMe over Fabrics for shared SSD pools
* **Computational storage**: Processing in storage devices
* **Persistent memory**: Byte-addressable, persistent (Intel Optane)
* **Zoned storage**: Append-only SSDs optimized for sequential writes

### Key Takeaways

* Multi-tier storage hierarchy optimizes cost and performance
* Parallel filesystems (Lustre, BeeGFS) essential for large-scale training
* Local NVMe caching reduces pressure on shared storage
* Dataset format matters: Use sharded, sequential formats
* Checkpoint strategy critical for fault tolerance and efficiency
* Object storage for long-term archival, not training
* I/O profiling identifies bottlenecks
* Proper data loading patterns prevent GPU starvation
* Storage network often separate from compute network
* Storage costs significant but manageable with tiered approach
